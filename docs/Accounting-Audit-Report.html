2. How it was checked

  • Automated tests of every feature (90 tests in 10 files), each run against the real database inside a transaction that is rolled back, so no test data remains.
  • New audit tests written for this audit (6 tests, file tests/accountingAudit.test.js): who may call what, company separation, bad and hostile input, exact tax arithmetic, 70 random operations, and the journal engine itself.
  • Regression run of the other (non-accounting) test files, to see that the accounting changes did not break the rest of the system.
  • Integrity check on the real data of the development company: trial balance, all 8 built-in checks, balance sheet, and direct database queries.
  • Code reading of the journal engine, the voucher confirm / un-confirm paths, invoice approve / un-approve, routes and permissions, and a scan for queries that are not limited to one company.

4. Features confirmed working

  • An entry always balances; a posted entry is never edited, only reversed; the database itself refuses to change posted lines.
  • Saving a voucher or invoice as a draft changes nothing in the books; confirming posts exactly one entry; moving back to draft posts a reversal and restores the paid amounts.
  • Two draft vouchers cannot spend the same bill twice: the second one is refused when it is confirmed.
  • Advances go to their own accounts with the party named; customer and vendor totals always agree with the control accounts.
  • Income tax withholding is exact (cheque + tax = bill amount for receipts; tax = bills x rate for payments).
  • Party Ledger, Payables / Receivables, Customer / vendor balances and the cut-off report give the same totals for the same date.
  • Profit & Loss, Balance Sheet and Trial Balance agree with each other; a contra account shows with the correct sign.
  • Every report and every screen is limited to the user's own company and to the services given to that user.

5. Findings

#LevelFindingAction
F1LowThe journal engine did not itself check that a customer / vendor named on a line belongs to the same company. Every screen already checked it, so no wrong entry could be made through the application; the engine just relied on its callers.Fixed The engine now checks it (PARTY_NOT_FOUND). A new test covers it. One older Trial Balance test had used an invented customer id on purpose; it now creates a real customer (the test was corrected, not the rule). All accounting suites were re-run after the change.
F2NoteSales and purchase invoice totals (gross, tax, net) are worked out with rounded ordinary numbers; vouchers, accounts and reports use exact whole-paisa arithmetic. The database column is exact to 2 decimals and the Trial Balance check compares each invoice with its ledger entry, so a difference would be shown.No change. Recommended later: move the invoices to the same exact arithmetic.
F3NoteSome updates and deletes work on a record by its id after the record was first loaded with a company filter. This is safe today, but the filter is not repeated in the second statement.No change. Optional hardening later.
F4Medium (missing feature)There is no period lock and no year-end closing. A user with full access can post or change vouchers dated in a month that is already finished.Not built yet. Recommended next: a "locked until" date per company, and a year-end close.
F5NoteVoucher numbers are the highest number plus one. If the last draft is deleted, its number is used again.Decision for the owner: keep (simple) or never re-use numbers.
F6NoteDuring the audit one request returned a server error while two test runs were using the same database at the same time. It did not repeat when the same test was run alone (three clean runs). In the same period another test file (greyReturn) reported "Client has encountered a connection error", so the most likely cause is the database connection being overloaded by two simultaneous test runs, not the accounting code. This is not proven, so it is reported here and not hidden.Watch for it in real use; run the real npm test on a separate test database.

6. What could not be tested here

The standard test command (npm test) needs a separate empty database called erp_test, which does not exist yet. The audit used a rollback runner on the development database instead. Because of this:
  • 2 accounting tests cannot run in the rollback runner (not failures of the code): the test that opens two connections at the same moment to prove that many users adding accounts never get the same code, and the test that checks that the database refuses to change posted lines (it needs a transaction to fail, which the runner does not allow). They must be run once with the real npm test; until then they are unconfirmed.
  • Real simultaneous use by several people (true concurrency) was checked by reading the code (every confirm / approve takes a per-company lock) but not by a live stress test.

7. Not built yet (known gaps)

  • Period lock and year-end closing (finding F4).
  • Debit note for goods returned to a vendor; purchase bills without a store inward; expense bills.
  • A screen to apply an advance to an invoice (today: by a Journal Voucher).
  • Bank statement import and automatic matching; server-made PDF / Excel for reports; FBR upload.
  • Comparison with a previous period, cash-flow statement.

8. Before going live

  1. Create the erp_test database and run the real npm test; every file must pass.
  2. Restart the server; the super admin must give the new services to the company: Purchase Invoice, Accounting Reports, Payment / Receipt / Journal Voucher, Bank Summary.
  3. Take a backup of the production database before running the new migrations (12 migrations, 24 to 30 October).
  4. Enter the opening balances through the Opening Balances screen, then check the Trial Balance and the Balance Sheet (both must balance).
  5. Decide about the period lock (F4) before real month-end work starts.
  6. Nothing has been committed to git yet. Use a branch and a pull request, not the main branch.
